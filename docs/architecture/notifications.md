# Notification Architecture

## Current implementation

Priority notification behavior is implemented for seller notification events generated by manual or scheduled priority review. Buyer notification delivery remains deferred until buyer notification rules are approved.

## Flow

1. Questions are classified at creation and during eligible review windows using the shared priority policy.
2. High Priority and Critical open questions qualify for notification events.
3. Notification events are batched by notifiable target, channel, and review date.
4. Scheduled review preserves duplicate-safe one-execution-per-UTC-window behavior.
5. Operations manual review can intentionally resend same-day seller batches through manual override grouping keys.
6. Delivery is delegated to outbound notification channel drivers selected by channel type.

## Boundaries

- Domain owns notification data structures, not delivery protocols.
- Application services orchestrate event creation and delivery through ports.
- Channel drivers own protocol-specific delivery behavior.
- The MVP console driver writes enabled email-channel payloads to stdout or an injected writer.

## Approved direction

- REST remains the command boundary for manual priority review.
- Scheduler and HTTP adapters invoke the same Operations application use case.
- Disabled channels are skipped deterministically.
- Unsupported enabled channel types return deterministic delivery errors at the driver boundary.

## Future options

- Slack, SMS, or other providers can be added behind the driver boundary.
- Buyer notifications require separate approved buyer target, trigger, and copy rules.
- Durable event delivery, retries, and delivery tracking remain outside the MVP.
